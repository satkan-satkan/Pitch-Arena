# PostgreSQL: запуск, перенос и восстановление

Приложение использует PostgreSQL через `pg`. SQLite оставлена для чтения прежних данных и быстрых тестов; при недоступном PostgreSQL сервер не переключается на SQLite незаметно.

## Локальный запуск

В `.env` задать `DATABASE_URL`, например `postgresql://localhost:5432/pitch_arena`. В локальном Postgres.app используется системный пользователь, если пользователь не указан в URL. На текущей машине проверен PostgreSQL 18.6 и создана отдельная база `pitch_arena`; другие базы не изменяются.

Для новой установки создать базу через Postgres.app или `createdb pitch_arena`, затем:

```sh
npm install
npm run db:migrate
npm run dev:all
```

Сервер при старте тоже применяет недостающие миграции. Файлы миграций находятся в `server/migrations`; журнал `schema_migrations` хранит имя, контрольную сумму и дату. Применённые SQL-файлы не редактируют: для изменений добавляют следующий файл. Блокировка PostgreSQL предотвращает параллельное выполнение миграций. Изменённая контрольная сумма или неизвестная новая миграция останавливает запуск.

Схема сохраняет строковые ID существующих данных; тексты JSON предыдущей версии переносятся без изменения. `001_core` создаёт пользователей, входы, проекты, сессии, файлы и импортированную историю. `002_admin` добавляет роли, блокировку пользователей, каталог, аудит и журнал импорта. `003_community` добавляет команды, приглашения, стартапы и снимки публикаций.

`DATABASE_URL` хранится только на сервере, не имеет префикса `VITE_` и исключена из Git. Настройки TLS зависят от среды; проверка сертификатов не отключена кодом приложения. Railway пока не настраивалась.

## Перенос SQLite

Перед переносом остановить старый API, чтобы новые записи не остались в прежней базе после создания снимка. PostgreSQL-цель должна быть пустой по пользовательским таблицам; системный каталог может быть уже заполнен.

```sh
npm run db:import-sqlite
```

Необязательный аргумент — путь к исходной SQLite. По умолчанию `.data/pitch-arena.sqlite`.

Мигратор:

1. Открывает исходник только для чтения и создаёт согласованную копию через SQLite backup API, включая актуальное содержимое WAL.
2. Сохраняет копию БД и загруженных слайдов в `.data/backups/<timestamp>`; проверяет наличие и размер файлов.
3. В одной транзакции переносит аккаунты, хеши паролей, токены входа, проекты, сессии, метаданные файлов и импортированную историю. ID и связи сохраняются.
4. Сравнивает все перенесённые поля и количество записей, затем фиксирует контрольную сумму импорта. При несовпадении транзакция откатывается.
5. Повтор того же снимка возвращает `alreadyImported:true`. Слияние с непустой новой базой запрещено, чтобы не затереть изменения.

Исходная SQLite и файлы не удаляются. Пути слайдов остаются прежними; при переносе на другую машину нужно перенести файловое хранилище и отдельно обновить пути. В текущем локальном переключении исходная серверная база была пустой; заполненный перенос с сохранением входов и слайдов проверен отдельным интеграционным тестом. Гостевой localStorage мигратор не трогает; его импорт доступен в аккаунте.

## Транзакции и конкурирующие запросы

Все запросы одной транзакции используют один `pg`-клиент через AsyncLocalStorage. Изменения тренировки защищены advisory lock по ID сессии и `revision`; состояние повторно читается после получения блокировки. Ответ HTTP отправляется после commit. Повторный `/complete` возвращает сохранённый результат. Административные изменения и аудит тоже атомарны.

Основа реализации: [транзакции node-postgres](https://node-postgres.com/features/transactions), [блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

API пока запускается одним экземпляром: лимиты запросов в памяти и файловое хранилище локальные. Хотя блокировка сессий теперь общая в БД, для нескольких экземпляров нужны общее хранилище файлов, распределённые лимиты и очередь ИИ. Внешний анализ выполняется в пределах транзакции с тайм-аутом провайдера; вынос длительных задач в очередь — следующий эксплуатационный этап.

## Резервная копия и возврат

Для согласованной резервной копии остановить API, сделать `pg_dump -Fc -d pitch_arena -f pitch-arena.dump` и скопировать `.data/assets`. Затем запустить API. Хранить копию в защищённом месте вне публичных файлов проекта. Проверять восстановление в отдельную базу, не поверх работающей.

Сразу после перехода можно вернуть прежнюю версию приложения `197426c` в отдельном checkout и исходную SQLite из резервной копии. Новые изменения PostgreSQL не попадут обратно в SQLite автоматически, поэтому после начала новой работы простой откат означает потерю этих новых записей. Сначала сохранить PostgreSQL и файлы, затем планировать обратный перенос.

Тестовый возврат к резервной SQLite проверяется чтением её данных отдельно от PostgreSQL; рабочая база никогда не удаляется тестами.

## Проверки

- `npm test` — быстрые правила и API на SQLite-адаптере для тестов.
- `npm run test:postgres` — реальные PostgreSQL-транзакции, права, каталог, конкурирующие запросы и импорт.
- `PA_TEST_POSTGRES=1 node --env-file-if-exists=.env --test tests/server.test.js` — прежние сценарии API на PostgreSQL.
- `npm run build && npm run test:admin` — браузерная проверка админки на PostgreSQL.

`TEST_DATABASE_URL` может указывать на отдельную тестовую БД, иначе используется `DATABASE_URL`. Тесты создают случайные схемы `pa_test_*`, применяют миграции и удаляют только собственную схему. Пользовательские таблицы `public` не трогают. Нужны права на создание тестовой схемы. Браузерные тесты используют отдельный контекст и временный сервер; живой OpenAI не вызывают.
